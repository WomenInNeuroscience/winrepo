# Backups & Restore Runbook

Operational documentation for [winrepo.org](https://www.winrepo.org): what is
backed up, how, where it lives, and how to restore it.

_Last updated: 2026-08-30_

## What gets backed up

| Asset | Backed up? | Mechanism | Where |
|-------|:----------:|-----------|-------|
| **Database** (MySQL) | ✅ Automated daily + on demand | `tools/backup_db.sh`, `tools/pull_db.sh` | `~/backups/` on PythonAnywhere; local `backups/` |
| **Configuration** (`.env`) | ⚠️ Manual | Copy on change | Stored off-server (holds secrets — see below) |
| **Code** | ✅ Continuous | Git | GitHub `WomenInNeuroscience/winrepo` |
| **User-uploaded media** | — N/A | none needed | The data model has no upload fields; profile images are external/static URLs |
| **Collected static** (`static-collected/`) | — Not needed | Regenerated by `collectstatic` | Rebuilt on deploy; source lives in the repo |

The only stateful asset that needs deliberate backup is the **database**.
Everything else is either in Git, regenerable, or a single config file.

## 1. Database

### Where backups live
- **On PythonAnywhere:** `~/backups/`, filenames `*_<DB_NAME>_<timestamp>.sql.gz` (gzipped SQL dumps).
- **Locally (when pulled):** `backups/` at the root of your clone.

### Automated daily backup
`tools/backup_db.sh` runs on PythonAnywhere, scheduled as a **daily task at
00:00** via the PythonAnywhere **Tasks** tab.

- Dumps the production DB with `mysqldump` (`--single-transaction --routines
  --no-tablespaces --column-statistics=0` — these flags are required on
  PythonAnywhere's shared MySQL).
- Writes a gzipped dump to `~/backups/`.
- **Retention:** automatically prunes dumps older than **30 days** (`KEEP_DAYS=30`).
- Reads DB credentials from `~/winrepo-prod/.env` (`DB_HOST`, `DB_NAME`,
  `DB_USER`, `DB_PASSWORD`).

To run it manually on the server:
```bash
cd ~/winrepo-prod
bash tools/backup_db.sh
```

### Pull a backup to your local machine
`tools/pull_db.sh` SSHes into PythonAnywhere, dumps the DB to a temp file,
downloads it to `backups/`, and cleans up the remote temp file.

```bash
./tools/pull_db.sh
```
Prerequisites: SSH access to PythonAnywhere (your public key in the server's
`~/.ssh/authorized_keys`) and DB vars present in `~/winrepo-prod/.env`.

### Restore the database
A backup is a gzipped SQL dump. To restore it into a MySQL database:

```bash
# Inspect first if unsure
gunzip -c backups/<DB_NAME>_<timestamp>.sql.gz | head -40

# Restore into the target database (will overwrite existing data)
gunzip -c backups/<DB_NAME>_<timestamp>.sql.gz \
  | mysql -h "$DB_HOST" -u "$DB_USER" -p"$DB_PASSWORD" "$DB_NAME"
```

> ⚠️ Restoring overwrites the target database. For a production restore, take a
> fresh backup of the current state first (`bash tools/backup_db.sh`) so you can
> roll back if the restore is wrong.

## 2. Configuration (`.env`)

The production `.env` (in `~/winrepo-prod/` on PythonAnywhere) holds everything
the app needs that isn't in Git: DB credentials, `SECRET_KEY`, reCAPTCHA keys,
Google/social-auth keys, the Google Maps key, and the Brevo SMTP credentials.

- **Back it up** whenever it changes — copy it somewhere safe off-server (a
  password manager or encrypted store).

> 🔐 **This file contains live secrets.** Do not commit it to Git, paste it into
> tickets, or store it unencrypted. If it is ever exposed, rotate every key it
> contains.

### Restore configuration
Copy the saved `.env` back to `~/winrepo-prod/.env` on the server, then reload
the web app (PythonAnywhere **Web** tab → **Reload**, or re-run the deploy).

## 3. Full disaster recovery (rebuild from scratch)

If the PythonAnywhere account or app is lost entirely:

1. **Code** — clone the repo: `git clone git@github.com:WomenInNeuroscience/winrepo.git`
2. **Config** — restore `.env` from your off-server backup (Section 2).
3. **Virtualenv** — `python3.10 -m venv .venv && source .venv/bin/activate && pip install -r requirements.txt`
4. **Database** — create an empty MySQL DB, then restore the latest dump (Section 1).
   If starting clean instead, run `python manage.py migrate`.
5. **Static** — `python manage.py collectstatic --noinput`
6. **Web app** — point PythonAnywhere's WSGI config at the project and reload.

The routine deploy itself is automated by `tools/refresh_env.sh` (pull, install,
collectstatic, migrate, reload), run by the **Deploy to PythonAnywhere** GitHub
Actions workflow. The workflow declares a `push` trigger on `main`, but pushes
do not currently start it — deploys must be started by hand from the repo's
**Actions** tab via **Run workflow** (`workflow_dispatch`). This is an
organisation-level Actions setting that an org admin needs to look at.

## Health checklist (review quarterly)

- [ ] The daily backup task is still enabled in the PythonAnywhere **Tasks** tab.
- [ ] `~/backups/` contains a dump from the last 24h and several recent days.
- [ ] A test restore into a scratch DB succeeds (don't only trust that dumps exist).
- [ ] A current copy of `.env` is saved off-server.
- [ ] Disk usage on PythonAnywhere is within plan limits (dumps + retention).
